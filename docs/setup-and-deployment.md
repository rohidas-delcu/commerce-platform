# Backend foundation setup and deployment prerequisites

## Supported development workflow

Use the existing checkout in isolated cloud tasks; do not create a worktree unless
explicitly requested. Run repository commands from the checkout root. Required:
Node.js 24, pnpm 11.25.0 (`packageManager`), and PostgreSQL 17 for database checks.
`apps/api` is the single NestJS application. `packages/database` owns the schema,
migration history and typed Prisma configuration. No additional runtime service
or frontend is required. The generated client belongs to the API and is ignored.

```sh
cp .env.example apps/api/.env # only if no local file exists
pnpm install --frozen-lockfile
pnpm db:validate
pnpm db:generate
pnpm test
pnpm typecheck
pnpm build
pnpm test:integration
```

Cloud machines with a read-only home can install with
`pnpm install --frozen-lockfile --store-dir /workspace/.pnpm-store`.
Dependency lifecycle scripts are explicitly allowed for Prisma and esbuild;
Scarf telemetry scripts are disabled. Do not disable TLS, artifact checksums or
package-signature verification. Prisma requires HTTPS access to
`binaries.prisma.sh`; npm uses `registry.npmjs.org`. GitHub PRs and Actions status
need `api.github.com`, separately from the platform's Git HTTPS proxy.

## Disposable PostgreSQL verification

The following credentials are examples for a loopback-only development database.
Do not reuse them for deployment. Preserve any existing container and use a new
name/port if the documented name is already in use.

```sh
docker run -d --name commerce-phase0-postgres \
  -p 127.0.0.1:5432:5432 \
  -e POSTGRES_USER=commerce -e POSTGRES_PASSWORD=commerce \
  -e POSTGRES_DB=commerce_test postgres:17-alpine
docker exec commerce-phase0-postgres pg_isready -U commerce -d commerce_test
export DATABASE_URL='postgresql://commerce:commerce@127.0.0.1:5432/commerce_test?schema=public'
pnpm db:deploy
pnpm db:deploy # second invocation must apply nothing
pnpm db:status
pnpm db:drift
pnpm test:database
pnpm test:postgres
```

Use a **disposable database**: repository tests briefly create test triggers to
force a rollback, and API tests retain uniquely named stores. Database tests need
DDL privileges. The application's future deployment role should have only the
privileges it needs; use a separate migration role. `db:deploy` applies committed
migrations; use `db:migrate --name <description>` only while authoring a new
migration against a development database with appropriate shadow-database access.
Never use reset or db push to replace deployment migrations.

The initial migration includes PostgreSQL CHECK constraints that Prisma does not
model: exact positive minor-unit money bounds, compare price ordering, stock
bounds, movement delta consistency and allowed movement reasons. Keep these
constraints when authoring future migrations. Prisma drift checks do not replace
the database constraint tests. UUID defaults are generated by Prisma, not by
PostgreSQL extensions. Inventory references use composite tenant keys.

## Runtime configuration and operations

Copy the example env file to `apps/api/.env`; Nest startup runs with that working
directory. The root Prisma configuration also loads that file. Existing exported
variables take precedence. Never commit real connection URLs or credentials.

| Variable | Requirement |
| --- | --- |
| `NODE_ENV` | Explicit `development` or `test`; unknown/unset values fail. Production always refuses startup pending real authentication. |
| `DATA_DRIVER` | `memory` (default) or `postgres`; unknown drivers fail. |
| `DEMO_AUTH_ENABLED` | `true` or `false`; demo headers accepted only with `true` and `NODE_ENV=development`. |
| `DATABASE_URL` | PostgreSQL URL required in postgres mode and by Prisma CLI. Adapter honors its `schema` parameter. |
| `PORT` | Integer 1–65535, default 3000; server binds only to `127.0.0.1`. |
| `CORS_ORIGINS` | Comma-separated exact HTTP(S) origins, default `http://localhost:5173`; wildcards and paths rejected. |

```sh
NODE_ENV=development DATA_DRIVER=memory DEMO_AUTH_ENABLED=true pnpm dev
# For the already-built persistent API:
NODE_ENV=development DATA_DRIVER=postgres DEMO_AUTH_ENABLED=true pnpm --filter @commerce/api start
```

`GET /health` is process liveness. `GET /health/ready` checks the repository and
required database tables/columns, returning 503 on failure. PostgreSQL startup
connects and checks the schema before listening. Pool connections have a 5-second
connect timeout and a maximum of 10 connections per process. Nest shutdown hooks
release Prisma's pool on SIGTERM/SIGINT; failed startup closes the application.
Live processes do not survive a cloud snapshot: restart the database and API.

Application logs are JSON. Startup configuration errors identify the invalid
setting without printing its value. Unexpected application/driver errors are
sanitized; HTTP errors use `{statusCode, code, message}`. Do not add logging of
headers, request bodies, SQL parameters or credential-bearing connection URLs.

## Deployment gate

A production build is a compilation check, **not deployment authorization**.
Phase 0 intentionally refuses production startup. Before any production exposure,
implement and review real merchant authentication/authorization in an approved
later phase, remove demo access through that reviewed design, configure TLS,
network isolation, secret management, database backups/restores, least-privilege
roles, monitoring and deployment migration procedures. CORS is not authentication.
A demo subject header can impersonate merchants and must remain local development
only. No payments, React implementation or additional microservices are included.

Do not merge or begin Phase 1 until Phase 0's PR and verification are reviewed.
